# Experiment: Jev typed classifiers as the IntentSpec reasoning stage

Status: run 2026-09-24 on all three datasets, arms A to E. Arm C on the
held-out set went through the logged-in `claude` CLI (`--llm-transport cli`
on `scripts/evaluate_intent_classifiers.py`) because the API account had no
credit. Results and decision in `reports/jev-intent-classifier-eval.md`.

## Question

Does replacing the regex gating in `ner.py` (operator choice, constrained enum
fields, resolver gate) with Jev typed classifiers produce a more accurate and
better-calibrated `IntentSpec` on phrasings the regex patterns have never seen,
at a latency and cost the hybrid server can absorb?

The deterministic assembler, `constrain.py` and `validate.py` stay exactly as
they are. Jev never emits ADS syntax; it answers bounded questions whose
answers are enum values already legal in `IntentSpec`. Names, years and topic
spans still come from the existing regex extractors in `ner.py`.

## Why this is worth running

- The current operator gate is 60+ hand-written regexes (`OPERATOR_PATTERNS`).
  Every "new patterns from US-004" comment marks a benchmark failure that was
  fixed by adding a regex. The 301-item benchmark is therefore contaminated:
  the patterns were written to pass it, and its 98.7% pass rate says nothing
  about unseen phrasing.
- `_set_confidence_scores` assigns constants (0.95 for any operator match).
  The server's `PIPELINE_CONFIDENCE_THRESHOLD` routes on a number that carries
  no information about the specific query. Jev returns a probability
  distribution over the options, which is the thing the router needs.
- The earlier end-to-end model conflated topic words with operators. Jev cannot
  emit syntax at all, so the failure class the hybrid pipeline was built to
  eliminate is structurally impossible for it too. The open question is only
  whether its classifications are right.
- Published numbers (TypeSafe launch post, softwaredoug WANDS post): 70 to
  500 ms end-to-end, $0.042 per million input tokens, output free, choice
  answers with per-option probabilities. The softwaredoug result that matters
  here is the precision/coverage trade-off: a general LLM with an "Unknown"
  option still guesses; Jev's confidence supports a tunable abstention
  threshold. Our recorded omni-experiments canary shows 171 to 349 ms per
  call against `api.typesafe.ai/v1/systemone` with `jev-1.13.0`.

## What Jev is asked

One System One request per query. `state` is `{"query": <nl text>}` only
(arm D adds the regex IntentSpec). Questions, all with criteria text derived
from the gating tables in `HYBRID_PIPELINE.md` and the ADS field docs:

| id | type | options |
|----|------|---------|
| `operator` | choice | none, citations, references, similar, trending, useful, reviews |
| `search_kind` | choice | topic, author, object, paper_reference, identifier, mixed |
| `refereed`, `openaccess`, `eprint` | boolean (`noul` on the wire) | property flags, multi-label |
| `doctype` | choice | none plus the values of `DOCTYPES` that appear in the benchmark |
| `bibgroup` | choice | none plus `BIBGROUPS` |
| `collection` | choice | none, astronomy, physics, general, earthscience |
| `needs_clarification` | boolean | ambiguous or underspecified request |
| `refers_to_specific_paper` | boolean | replaces `needs_resolution` heuristics as the resolver gate |

Response fields used: `answers.<id>.choice`, `.confidence`, `.probabilities`
for choice; `.noul` probability for boolean; `usage.input_tokens`; `model`.
The model id is pinned to the version observed in the smoke call, not
`jev-latest`, and the response model id is recorded on every row.

## Arms

| arm | intent source | purpose |
|-----|---------------|---------|
| A | regex `extract_intent` as shipped | baseline, zero cost |
| B | Jev for operator, enums, gates; regex for names, years, topics | the proposed change |
| C | general LLM (Claude Haiku 4.5, structured output, same schema, explicit `unknown` per field) | separates "typed decomposition helps" from "Jev helps" |
| D | as B, with the regex IntentSpec included in `state` | does structural context help or bias Jev |
| E | regex first; Jev only when regex sets no operator or pipeline confidence < 0.5 | the deployable shape, cost-minimal |

Arm C exists because the softwaredoug post and the omni plan both insist on
it: without it a Jev win cannot be attributed to Jev rather than to asking
narrow questions.

## Datasets

1. **Benchmark (301, contaminated).** `data/datasets/benchmark/benchmark_queries.json`.
   Used for interface debugging and for picking abstention thresholds only.
   Never used to report the headline number. The 15 `topn` items have no
   `IntentSpec` operator; they are labelled `operator=none` and reported
   separately.
2. **Held-out synthetic (478).** `data/datasets/processed/val.jsonl`. NL was
   generated by Claude Sonnet 4 from real ADS log queries, so phrasing leans
   toward query structure. Gold labels are derived mechanically from the gold
   ADS query (see Labels). Items whose gold query cannot be parsed into
   IntentSpec-compatible fields are dropped and the drop count reported.
3. **Held-out paraphrases (target 150, new).** Stratified:
   40 operator-positive whose phrasing matches no regex in `OPERATOR_PATTERNS`
   (asserted mechanically: regex arm must return `operator=None`),
   40 operator-negative with operator words as topic ("citation analysis
   techniques", "trending towards lower masses"),
   40 enum synonyms outside the synonym maps ("gold open access", "Chandra
   data", "conference talk", "planetary science collection"),
   30 ambiguous or clarification-worthy. Every item is human-reviewed before
   any model sees it; if drafts are LLM-generated, that model is named in the
   file and excluded from arm C.

This is the set on which the regex arm is expected to fail by construction.
It measures generalisation beyond the pattern set, which is the property the
experiment is about. It is stated plainly in the report that regex could be
extended to pass it; the point is that Jev does not need to be.

## Labels

`scripts/derive_intent_labels.py` parses a gold ADS query into
`{operator, property, doctype, bibgroup, collection, has_year, has_author}`
using field-prefix matching against `FIELD_ENUMS`. This is mechanical, not
semantic, so it stays in code. It is unit-tested against the benchmark's
`operator` and `enum_value` fields, which are already present and serve as a
cross-check. `search_kind`, `needs_clarification` and
`refers_to_specific_paper` have no derivable label and are scored only on
the paraphrase set, where they are hand-labelled.

## Metrics, pre-registered

Per field, on each dataset, per arm:

- Operator: 7-class macro-F1, per-class precision and recall, and the
  false-positive rate on the operator-negative stratum (regex is near 0 there
  by construction; Jev must stay at or below 2%).
- Enum fields: set F1 per field.
- Selective accuracy vs coverage at confidence thresholds 0.5 to 0.95, using
  Jev `confidence` (arm B, D, E) and the LLM's `unknown` rate (arm C).
- Calibration: reliability bins and expected calibration error on the
  operator `confidence`. TypeSafe's "calibrated" claim is measured, not assumed.
- Stability: 3 repeats on a 100-item subset of the paraphrase set; report
  the fraction of items whose top choice changes.
- End to end: assembled query syntax validity, exact match, and result-set
  Jaccard against the gold query via `scripts/evaluate_semantic_overlap.py`
  extended with `--intent-backend`. Needs `ADS_API_KEY`.
- Latency p50 and p95 per arm, measured client-side from this machine, and
  cost per query from reported `usage.input_tokens` at the published rate.

## Success criteria, fixed before the first run

Go (replace regex gating with arm E in `hybrid` routing) requires all of:

1. Arm B operator macro-F1 on the paraphrase set exceeds arm A by at least
   15 points, and exceeds arm C.
2. Arm B false-positive rate on the operator-negative stratum is at most 2%.
3. At 90% coverage, arm B selective operator accuracy is at least 95%.
4. End-to-end semantic match on the benchmark does not drop versus arm A
   (no regression on the contaminated set), and rises on the held-out sets.
5. Arm E p95 added latency at most 600 ms, mean cost at most $0.0001 per query.

Partial outcome: criteria 3 and 5 hold but 1 does not. Then Jev is adopted
as the confidence signal for routing only, and regex stays as the extractor.

No-go: criterion 2 fails. Conflation was the reason the hybrid pipeline
exists; a classifier that reintroduces it is not adopted regardless of other
gains.

## Cost and budget

Roughly 930 items across the three datasets, three Jev arms, plus 300
stability repeats, at about 1.2k input tokens per call: near 4 million input
tokens, under $0.20 at the published rate. Arm C is a few dollars at most.
Every request is cached to JSONL by request fingerprint so re-scoring is
free and reruns only pay for new items.

## Implementation steps

0. Smoke call from Python (`httpx`) to `https://api.typesafe.ai/v1/systemone`
   with one choice and one boolean question. Confirms the wire contract the
   omni-experiments runner encodes (`type: "noul"` for boolean, `answers`
   envelope, `model`, `usage`) and records the current model version.
1. `domains/scix/jev_intent.py`: question set builder, client, response to
   partial `IntentSpec` plus a real `confidence` dict. IO, schema validation
   and caching only; no keyword logic.
2. `extract_intent_jev(text, client)` composes Jev answers with the regex
   extractors for years, authors and topics. `process_query` and the server
   gain an `intent_backend` setting: `regex`, `jev`, `jev_gated`.
3. `scripts/derive_intent_labels.py` with unit tests.
4. `data/datasets/benchmark/heldout_paraphrases.json` plus a check script
   asserting the operator-positive stratum is out-of-pattern for regex.
5. `scripts/evaluate_intent_classifiers.py`: runs arms A to E, writes one
   JSONL row per (arm, item, repeat), produces the metric tables above.
6. `--intent-backend` on `evaluate_semantic_overlap.py`.
7. `reports/jev-intent-classifier-eval.md`: the criteria table filled in,
   decision, and the caveats below restated with whatever numbers apply.

## Caveats carried into the report

- Benchmark contamination with the regex patterns.
- Synthetic NL in `val.jsonl` was generated from queries, so it may be easier
  than user input for every arm.
- Jev confidence is a model output. Whether it is calibrated on this task is
  a result of this experiment, not a premise.
- `jev-latest` can change under us; the model id is pinned and logged.
- Operator target resolution (bibcodes, "this paper") remains the resolver's
  job; Jev only decides whether the resolver should run.
- Latency is measured from this machine to TypeSafe; production placement
  may differ.
- No real user queries are in any dataset. The 91k-row ADS log CSV is ADS
  syntax, not natural language, and cannot serve as NL input.
